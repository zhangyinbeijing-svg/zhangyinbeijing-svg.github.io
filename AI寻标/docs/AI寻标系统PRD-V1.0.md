## 〇、图片核心思想提炼（本 PRD 的撰写依据）

> 本章内容全部提炼自《寻标系统核心思想》骨架图，是后续所有章节的设计依据；图片未覆盖的部分在 0.5 节单独标注。

### 0.1 核心思想

系统以「**让招标信息找得准、企业匹配对得上、投标文件写得出、投标效果回得来**」为核心思想，构建一条五段式主链路，并通过数据回流形成持续优化的闭环：

**招标信息检索 → 企业画像 → 智能匹配 → 标书生成 → 闭环优化**

- **数据是地基**：多源采集 + 解析 + 结构化 + 校验，保证招标信息"全、准、新、可溯"；
- **画像是底座**：把企业基本情况、资质、业绩、团队结构化、标签化，形成可被机器匹配的企业能力模型；
- **匹配是引擎**：规则 + 语义 + 多维评分，把"项目要求"与"企业能力"对齐，并经过召回率/准确率校验，保证推荐可信；
- **生成是出口**：从招标文件解析到模板化生成再到合规校验，把投标建议落到可提交的投标文件；
- **闭环是进化**：用推荐率、中标率等实效数据做归因分析，反向驱动规则、权重与模型的持续迭代。

### 0.3 关键流程（由图片推导的主干数据流）

1. 从政府采购网、招标平台、企业官网采集招标公告；
2. 下载附件，经 OCR / PDF 解析得到原文内容；
3. 标题拆分、重复识别完成结构化与去重；
4. 字段完整性、来源可溯、及时更新三项校验合格后入库（数据库 + 向量库 + 备份）；
5. 用户通过关键词检索、AI 语义检索或订阅推送获取项目；
6. 项目侧做关键词提取、实体识别、标签提取；企业侧由画像（基本信息/资质/业绩/团队）提供匹配要素；
7. 规则评分 + 语义评分 + 多维评分得到匹配分并排序，经召回率/准确率验证后输出匹配报告（生成、推送、存档）；
8. 对拟投标项目：下载招标文件 → 要点提取、要求识别 → 选择内置/企业/行业模板 → 结构生成、内容填充、图表插入、校对 → 真实性、格式、敏感信息三重合规检查 → 产出投标文件；
9. 投标后回收推荐率、中标率、评分数据 → 优势/短板/对手归因分析 → 规则优化、权重调整、模型迭代 → 数据回流，闭环运行。

### 0.4 产品价值

- **对投标企业**：把"人肉盯标、经验判断、手工写标"升级为"自动寻标、量化匹配、智能写标"，扩大商机覆盖、降低漏标错标风险、压缩投标成本；
- **对市场/商务人员**：从重复信息搜集中解放，聚焦商机判断与客户经营，匹配报告为"投不投"提供量化决策依据；
- **对标书撰写人员**：从解析招标文件、套模板、填内容等重复劳动中解放，聚焦方案打磨与质量把关；
- **对企业管理层**：通过闭环优化模块沉淀投标实效数据，形成可量化的投标能力评估与改进机制。

## 一、产品背景与产品目标

### 1.1 背景与问题

投标是大量 ToB/ToG 企业的核心获客方式，但投标全链路长期存在四类痛点：

| 痛点 | 现状描述 | 后果 |
| --- | --- | --- |
| **信息获取难** | 招标信息分散在政府采购网、各地公共资源交易中心、招标平台、企业官网等数百个渠道，靠人工每日巡检 | 漏标、迟标，商机覆盖率低 |
| **商机判断难** | 项目是否值得投、企业条件是否满足，依赖个人经验，无量化标准 | 盲目投标浪费资源，或错失可中标项目 |
| **标书撰写难** | 标书编写周期长（常见 3~7 天），格式要求严苛，人员水平参差 | 响应不全、废标风险高、人力成本高 |
| **经验沉淀难** | 投标结果（中/未中、得分）散落，缺少复盘机制 | 同类错误反复出现，投标能力无法迭代 |

### 1.2 产品定位

**AI 寻标系统 = 招标商机智能发现 + 企业能力匹配评估 + 投标文件智能辅助撰写的一体化投标效能平台。**

一句话定位：让企业"找得到标、投得对标、写得好标、越投越准"。

### 1.3 产品目标（保持不变，来自产品定义）

> 帮助用户**联网收集招标信息**，**结合企业自身情况进行匹配**并**给出投标建议**，最终**辅助用户撰写投标文件**。

分解为四个可度量目标：

1. **找得到**：招标信息全网采集、及时更新、可检索可订阅；
2. **配得准**：项目要求与企业资质/业绩/团队自动匹配，输出可信的匹配度与建议；
3. **写得出**：基于招标文件要求与模板库，辅助生成结构完整、内容可用的投标文件草稿；
4. **越用越准**：投标实效数据回流，持续优化匹配与推荐策略。

### 1.4 业务价值

- 商机覆盖率提升 → 可投标项目数量增长；
- 投标决策量化 → 减少无效投标，资源聚焦高胜率项目；
- 标书编写提效 → 单份标书平均编写时长显著下降；
- 数据资产沉淀 → 企业信息库、资质库、业绩库、模板库成为企业核心资产。

## 二、目标用户与典型场景

### 2.1 用户角色

| 角色 | 与系统的关系 | 核心诉求 |
| --- | --- | --- |
| 招标方（采购人/代理机构） | 信息**来源方**：其公告构成系统数据源；远期可作为独立角色使用系统进行需求梳理与应标分析 | 本期不作为系统使用方；涉及其公告数据的采集需合规（见第八章） |
| 投标企业决策者（老板/总经理） | 使用者 + 买单者 | 快速看到值得投的项目、投标投入产出 |
| 市场/商务人员 | 高频使用者 | 第一时间发现商机，判断"能不能投、值不值得投" |
| 标书撰写人员 | 高频使用者 | 快速产出合规、高质量的投标文件草稿 |
| 企业资质/资料管理员 | 维护者 | 维护企业画像、资质证照、业绩案例，保证信息新鲜有效 |
| 系统管理员 | 管理者 | 账号权限、数据源配置、模板库管理、日志审计 |

> 用户角色与系统预置权限角色（租户管理员/管理员/商务市场/标书撰写/资料管理员/观察者）的对应关系见 7.1 节角色设计。

### 2.2 典型场景

**场景 1｜市场专员的早晨（信息发现）**
市场专员小李上班打开工作台，看到系统按订阅规则推送的 12 条新公告，其中 3 条带"高匹配"标记。他点开匹配度最高的一条，查看匹配明细：资质满足、类似业绩 2 个命中、地域可覆盖，系统建议"建议投标，预计匹配度 87 分"。他一键将项目加入"拟投标清单"。

**场景 2｜投不投的决策会（匹配与建议）**
商务总监对一个 500 万级项目犹豫不决。系统中该项目的投标建议报告显示：资质硬性条件全部满足，但"同类业绩 ≥3 个"仅满足 2 个（存在废标风险项），竞争对手可能具备本地化优势，综合建议"谨慎投标"。团队据此放弃该项目，避免了无效投入。

**场景 3｜三天标书一天写完（标书撰写）**
标书员小王接到拟投标任务。系统已解析招标文件并提取评分要点与硬性要求，按行业模板生成标书大纲与章节草稿，企业资质、业绩、团队内容自动填充。小王只需补充技术方案细节，系统校对发现 2 处格式问题、1 处资质有效期临近提示，修改后导出 Word/PDF 终稿。

**场景 4｜资质到期预警（画像维护）**
资料管理员收到系统提醒：某项资质将于 60 天后到期，而该资质关联 5 个在订阅中的招标方向。管理员完成资质更新后上传新证照，OCR 自动识别并刷新画像字段。

**场景 5｜季度投标复盘（闭环优化）**
季度复盘时，管理层在闭环优化看板看到：本季度推荐项目采纳率 62%、中标率 28%；归因分析显示"失分集中在技术方案章节"、"主要对手为 A、B 两家公司"。据此调整匹配权重（更重视业绩门槛），并将高分中标标书入库为企业模板。

## 三、核心业务流程

### 3.1 端到端主流程（七环节）

```
①招标信息联网采集 → ②信息清洗与去重 → ③项目筛选/订阅
        ↓                                    ↓
⑦闭环优化 ← ⑥审核与导出 ← ⑤投标文件撰写 ← ④a企业情况匹配 + ④b投标建议生成
```

| 环节 | 关键活动 | 对应图片模块 | 关键产出 |
| --- | --- | --- | --- |
| ① 联网采集 | 多源采集、附件下载、OCR/PDF 解析 | 01-数据来源/解析 | 原始公告 + 附件文本 |
| ② 清洗去重 | 标题拆分、重复识别、字段校验 | 01-结构化处理/数据校验 | 标准化项目数据（入库） |
| ③ 筛选订阅 | 关键词/语义检索、订阅规则、推送 | 01-检索方式 | 用户可见的项目列表与推送 |
| ④a 企业匹配 | 项目结构化 → 多维评分 → 排序 → 验证 | 04 + 03 | 匹配分、匹配明细 |
| ④b 投标建议 | 硬性条件核查、可行性评估、风险提示、推荐评分 | 04-报告输出 | 投标建议报告（生成/推送/存档） |
| ⑤ 标书撰写 | 招标文件解析 → 大纲生成 → 内容填充 → 人工编辑 | 05 | 标书草稿、版本记录 |
| ⑥ 审核导出 | 合规三重检查、人工审核、导出归档 | 05-合规 | 终稿文件、导出记录 |
| ⑦ 闭环优化 | 结果登记、效果统计、归因、策略迭代、数据回流 | 06 | 优化后的规则/权重/模型 |

### 3.2 关键分支与异常流程

| 场景 | 处理策略 |
| --- | --- |
| 采集失败/源站改版 | 任务告警 → 进入重试队列 → 超阈值通知运维；该源数据标记"更新异常" |
| 字段不完整（如缺预算金额） | 允许入库但标记"字段缺失"，检索结果中明示，不参与依赖该字段的匹配项计分 |
| 重复公告（变更公告/更正公告） | 重复识别后关联为同一项目族；更正公告覆盖原公告关键字段并留痕 |
| 硬性条件不满足 | 匹配报告明确列出"不满足项"，投标建议为"不建议投标/存在废标风险"，标书生成入口置灰或强提示 |
| 生成内容不可用 | 用户可整章重生成、单段改写；所有 AI 生成内容标注来源依据（招标文件条款号或企业资料条目） |
| 投标结果未回收 | 超期未登记结果的拟投标项目，系统定期提醒补录，保障闭环数据完整 |

- 通道 A 保障核心源自主可控，通道 B 补长尾覆盖与时效，降低长尾站点爬虫维护成本；

### 4.9 大模型选型与部署策略（行业经验设计，关闭 Q10）

**设计原则**：场景分层路由（什么任务用什么模型）、国产合规（数据不出境）、统一网关可切换、敏感数据脱敏上云或自部署。

**场景模型映射（推荐方向，具体供应商待 PoC 评测后确定）**：

| 能力场景 | 模型类型 | 推荐方向 | 部署建议 |
| --- | --- | --- | --- |
| 语义检索/向量化（01-向量库） | Embedding 模型 | 国产主流文本向量模型（BGE/通义 embedding 类） | 私有化部署（高频低成本） |
| 结构解析：实体识别/标签提取/要点提取（04-结构化、05-解析） | 7B–14B 轻量模型 | 微调开源小模型或 API 轻量模型 | 建议私有化（调用量大） |
| 语义评分与重排（04-评分） | Embedding + Reranker | 向量召回 + 重排模型两级架构 | 私有化部署 |
| 标书大纲/内容生成与改写（05-生成） | 通用大模型 | 国产主流大模型 API（通义/DeepSeek/GLM 类） | SaaS 用 API；私有化客户自部署 |
| 校对/敏感信息检查（05-合规） | 轻量模型 + 规则 | 小模型与敏感词规则库结合 | 私有化部署 |

**双轨部署策略**：
- **SaaS 标准版**：生成类任务调用国产主流大模型 API；与供应商签数据处理协议（零数据留存、不用于模型训练、数据不出境）；企业名、联系人、金额等敏感字段按策略脱敏后上云；
- **私有化/专属版**：开源模型（Qwen/DeepSeek/GLM 系列）全链路私有部署 + 推理加速（vLLM 类）；GPU 资源客户自备或租赁；高保密客户可先落地 embedding 与小模型私有化，生成类任务按需切换；
- **统一模型网关**：抽象统一接口层屏蔽厂商差异；支持多供应商切换、负载均衡与故障兜底；模型服务不可用时，匹配降级为规则 + 关键词方式，保障基础可用性。

**成本管控**：
- 分层路由：简单结构化任务走小模型，仅标书生成使用通用大模型；
- 结果缓存：同类招标文件/相同模板结构的解析结果缓存复用，减少重复调用；
- 预算监控：按租户配额与 Token 预算控制，异常消耗告警。

### 4.10 决策引擎组与决策输出标准化（依据《决策骨架 V3 优化版》，V2.1 新增）

**系统价值定位**：招投标前置风险研判 + 我方投标预评估——完成"风险体检 + 蓝图打分"，从源头减少无效投标、提高中标概率。本平台定位为投标辅助系统的**上游决策平台**：先完成"投不投、怎么投"的研判，决策投标后再进入下游标书撰写环节（4.6）。

**与同类平台差异**：不止做标书撰写，先对招标项目做全维度风险筛查与决策研判，再决定是否进入撰写流程。

#### 4.10.2 决策输出标准化

**单一真相源原则**：每个项目的决策结论以「★决策书」为唯一权威来源；投标建议页顶部摘要总览只能**派生展示**，不得重新解释，防止多处口径漂移。

**决策结论标准词库（四档，禁止使用模糊措辞）**：

| 结论 | 含义 | 展示色 |
| --- | --- | --- |
| GO | 建议投标 | 绿 |
| GO 附条件 | 建议投标，但须先满足列明的前提条件 | 蓝 |
| WATCH | 建议观察暂缓（条件不成熟/信息不足，持续跟踪） | 橙 |
| NO-GO | 建议放弃 | 红 |

**总体建议公式**：总体建议 = 决策结论文 + 策略名 + 前提条件。

**决策书标准构成**：
1. 决策结论（标准词库四档）与总体建议；
2. 五要素摘要：核心风险 / 关键机会 / 预算匹配度 / 竞争格局 / 推荐策略；
3. 执行清单：投标前必做的 10–15 项具体动作，每项含动作、责任人、截止时间、状态；
4. 风险登记表：风险项 = 评级 + 责任人 + 时间窗口 + 应对预案；
5. 双向预案：中标后下一步（合同/履约准备）与不中标后下一步（复盘/转投储备项目）——"双向预案，不浪费这次投标动作"。

**输出一致性校验清单（决策书交付前必检，≥3 项不通过即打回重做）**：

| # | 校验项 | # | 校验项 |
| --- | --- | --- | --- |
| 1 | 摘要结论文 = 决策书结论文 | 7 | 前置条件：摘要 ≥ 决策书核心前提 |
| 2 | 摘要策略 = 决策书策略名 | 8 | 全文无模糊结论 |
| 3 | 报价区间：市场调研 → 策略矩阵 → 决策书三处一致 | 9 | 核心产品均在产型号 |
| 4 | 核心产品方案：市场调研 → 策略 → 执行清单三处一致 | 10 | 核心产品产地符合采购文件要求 |
| 5 | 风险等级：风险筛查 → 风险登记表一致 | 11 | ≥3 项不通过 → 打回重做 |
| 6 | 弃标条件：决策书 ≥ 双向预案触发条件 | | |

#### 4.10.3 与现有模块的关系与优先级

- **与 4.4/4.5 的边界**：4.4 六维匹配分用于商机发现阶段的"值得看吗"（列表排序与推送）；4.10 引擎组用于单项目深度研判阶段的"能不能投、怎么投、扛不扛得下"（P06 决策页）。两者数据同源（企业画像 + 招标文件解析），职责分层；
- **与 F5-5 高级风险提醒的关系**：围标识别/竞品对比/价格风险并入 E1 第④层与 E2/E3 输出，F5-5 不再单列；条件类基础风险（F5-3）作为 E1 第②层的基础输入；
- **与 F5-2 推荐值的关系**：推荐值与推荐下限仍为推荐列表触发机制（决定项目是否进入用户视野）；E5 决策综合得分与标准决策结论为深度研判输出（决定项目投法），二者并存、页面分区呈现；
- **优先级**：E1 四层风险筛查、E5 三层量化评分、决策结论标准化输出、执行清单为 P0（MVP）；E2 市场调研、E3 历史中标格局、E4 指定性识别、E6 策略矩阵、风险登记表、双向预案为 P1（V1.1 交付，依赖历史数据积累与公开数据分析能力）。

### 5.3 数据与日志保留策略（分层设计，关闭 Q6）

设计原则：
- **合规底线**：安全审计日志与网络日志 ≥6 个月（等保三级、《网络安全法》）；
- **业务价值**：闭环优化依赖长周期历史投标数据、匹配报告与投标结果，冷热分层长期保留控成本；
- **隐私合规**：企业数据删除与账号生命周期联动，符合《个人信息保护法》。

| 数据/日志类别 | 热存（在线可查） | 冷归档 | 清理/删除策略 |
| --- | --- | --- | --- |
| 招标公告与原文快照 | 3 年 | 10 年 | 到期自动转冷存 |
| 匹配报告、投标建议、决策记录、投标结果 | 3 年 | 10 年 | 闭环优化数据底座，到期转冷不删除 |
| 标书终稿与导出记录 | 账号存续期 | — | 随账号注销删除 |
| 标书历史版本 | 1 年（每项目保留最近 50 版） | — | 超限旧版本可自动清理，终稿不删 |
| 企业画像/资质/业绩/团队 | 账号存续期 | — | 账号注销后删除（见下） |
| 订阅与推送记录 | 1 年 | — | 自动清理 |
| 审计日志（登录/敏感操作/权限变更） | 12 个月 | — | 滚动清理（等保三级底线 6 个月，设计留冗余） |
| 业务全链路日志（采集/匹配/生成/导出） | 12 个月 | — | 滚动清理 |
| 系统运行日志（监控/错误） | 90 天 | — | 滚动清理 |

账号注销与数据删除：
- 注销前提示用户导出企业数据（画像、标书、投标记录）；
- 注销确认后进入 30 天冷静期，期内数据冻结可恢复；冷静期满执行删除或匿名化；
- 法定义务需留存的（审计日志等）按法定期限留存，不随注销删除。

| 8 | 合规检查页 | 真实性/格式/敏感信息三类检查结果列表，逐条定位到正文 | 一键跳转修正；检查通过后解锁导出 |
| 9 | 导出记录 | 导出历史（时间/人/版本/文件）、重新下载 | 下载；查看关联版本 |
| 10 | 闭环看板（管理端） | 推荐率、中标率趋势、失分归因、对手对比 | 下钻到项目明细；触发规则调优入口 |
| 11 | 系统管理 | 账号权限、数据源管理、订阅管理、模板库管理、规则库管理、审计日志 | 管理员配置类操作 |

**通用交互原则**：
- 所有 AI 产出（匹配判定、生成文本）必须展示依据来源，并提供人工修正入口；
- 列表类页面默认按匹配分/推荐分排序，可切换为时间排序；
- 关键不可逆操作（删除画像数据、删除版本）需二次确认。

### 7.2 企业数据隐私

- 企业画像、资质、业绩、标书内容属于**核心商业机密**：传输加密（TLS）、存储加密、导出留痕；
- 企业数据**不得**跨租户用于模型训练或对外展示；用于系统优化时须脱敏并取得授权；
- 支持企业数据导出与账号注销删除（合规要求）；
- 调用第三方大模型 API 须签数据处理协议（零留存、不用于训练、数据不出境）；敏感字段按策略脱敏后上云；高保密客户提供私有化部署选项（见 4.9）。

### 7.3 招标信息合规使用（含采集合规边界，已关闭）

**基本原则**：采集对象以公开发布的招标公告为限；公开采集（通道 A）与授权 API（通道 B）两种方式均支持，但均须遵守以下边界。

**采集合规红线（通道 A）**：
1. 仅采集公开发布的公告内容；不采集需登录、付费、账号权限才能访问的内容；
2. 不绕过、不破坏目标站反爬、验证码、IP 封禁等技术保护措施；
3. 遵守 robots.txt 与目标站使用条款；条款明确禁止采集的，转通道 B 授权或放弃该源；
4. 限速采集（单站建议 ≤2 请求/秒，错峰执行），不影响源站正常运行；
5. 个人信息脱敏：招标人联系人姓名/电话、评标专家个人信息默认脱敏或不存储；
6. 展示内容保留原文链接与来源标注，不做歪曲篡改。

**授权通道要求（通道 B）**：
1. 第三方数据服务与平台官方 API 须商务合同/授权后接入，合同明确授权范围（使用方式、衍生加工、转分发限制）；
2. 付费数据服务内容不得原样对外转分发，仅限内部匹配、衍生与报告生成使用；
3. 合同明确数据权属、违约责任与服务中断处置预案。

**数据源准入流程**：申请 → 法务/合规审查（授权依据）→ 技术接入 → 上线；存量源每月合规抽查复审，源站条款变更时即时停用重评。

### 7.4 内容安全与审核

- AI 生成内容须通过敏感信息检查（涉密词、不当承诺、虚假业绩）后方可导出；
- **真实性红线**：标书引用的资质、业绩必须来自企业画像真实数据，系统禁止凭空编造并在合规检查中强制验证；
- 生成内容标注 AI 产出属性，最终提交责任由用户承担（产品内明示）。

### 7.5 等保三级合规要求（SaaS，已确认）

| 维度 | 要求 |
| --- | --- |
| 身份鉴别 | 强口令策略（≥8 位，含大小写字母/数字/特殊字符，90 天强制更换）；管理员账号强制 MFA；连续 5 次失败锁定 15 分钟 |
| 访问控制 | RBAC 最小权限原则；空闲会话 30 分钟自动断开；并发会话数限制；特权账号不可共享 |
| 安全审计 | 登录/登出、敏感操作、导出、删除、权限变更全量记录；审计日志防篡改（只增不改）；留存 ≥ 6 个月（设计为 12 个月，见 5.3） |
| 数据安全 | 传输 TLS 1.2+；资质证照、标书内容、企业画像等敏感数据落库 AES-256 加密；密钥与数据分离管理；每日增量 + 每周全量备份，异地容灾 |
| 网络安全 | 选用已过等保三级的云环境；部署 WAF、DDoS 防护、入侵检测；安全组最小化开放 |
| 双人双控 | 生产数据批量删除、敏感数据批量导出等高危操作需双人复核 |
| 合规流程 | 系统上线前完成等保备案与三级测评，每年复测；个人信息（手机号/邮箱等）处理符合《个人信息保护法》；数据不出境 |

## 附录 B：术语表

| 术语 | 定义 |
| --- | --- |
| 公告 | 招标方公开发布的招标/更正/中标/废标信息 |
| 项目 | 经结构化与去重后的招标对象，一个项目可含多个标段 |
| 企业画像 | 企业基本信息、资质、业绩、团队的结构化 + 标签化数据集合 |
| 匹配分 | 项目要求与企业能力按规则/语义/多维加权计算的综合得分 |
| 推荐率 | 超过用户配置的推荐下限的项目中被用户采纳（决策为"投"）的比例；统计口径见 4.8-F8-1 |
| 推荐下限 | 用户自行设置的推荐值阈值（默认 80，60–95 可调），超过下限的标的才被推荐投标 |
| 响应点 | 招标文件中要求投标方逐项应答的条款/评分项 |
| 闭环优化 | 以投标实效数据反向优化匹配与生成策略的持续迭代机制 |
